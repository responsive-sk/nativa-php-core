# A public form without the sibling form's bot defense (and an audit finding that was half wrong)

**Date:** 2026-10-16 00:02
**Files:** modules/Comments/Interfaces/HTTP/Actions/CommentSubmitAction.php, modules/Comments/Interfaces/HTTP/CommentSection.php, modules/Comments/tests/CommentHoneypotTest.php (new), docs/kernel-status.md
**Severity:** low

## Problem

`POST /blog/{slug}/comments` had no honeypot, while the tree's other public form
(`QuestionSubmitAction`) had one (`question_website`). A submission that filled
every field it found — the naive crawler a honeypot exists for — was accepted and
left a `pending` row in the moderation queue, indistinguishable from a reader's
comment. Measured before the change, through the real action on temporary
databases:

```
POST /blog/hello-world/comments (every field filled, incl. comment_website) => HTTP 302 /blog/hello-world#comments
comments stored: 1
  row: hello-world | Bot Probe | pending
```

## Root Cause

The defenses of the two public forms were written one form at a time, and only
one of them got the honeypot. Nothing in the tree compares siblings: Comments
was refactored for rate limiting (per IP+slug, before validation) and stopped
there, Questions was hardened later with both a limiter and a honeypot, and the
gap between the two was invisible to every gate — a form without a hidden field
still renders, still validates, still redirects.

**The audit finding itself was the second failure, and the more instructive
one.** It claimed the comments route had "only the global 60/min limiter". It
has carried a per-IP+slug limiter (10 per 60 s, loopback exempt, applied before
validation) since the module refactor; the claim was written from the action —
where no limiter is visible — without reading `CommentsService`, which is where
the call lives. A finding whose premise is not traced through the code produces
a fix for the wrong gap (here: a redundant per-IP limiter that the global
middleware already provides).

## Solution

- `CommentSection::form()` renders the honeypot in the shape the questions block
  already uses (`<prefix>-comments__hp`, `hidden`, `autocomplete="off"`,
  `tabindex="-1"`, label "Website") — a honeypot nobody renders catches nobody.
- `CommentSubmitAction` reads `comment_website` BEFORE any lookup or write and
  answers a filled one with the redirect a real submission gets: silent discard,
  no error page, nothing in the moderation queue. The field name and discard
  shape mirror `QuestionSubmitAction` so the two forms cannot drift.
- The docblock now states which defense is the boundary: the honeypot is a cheap
  filter for naive crawlers, the per-IP+slug limiter bounds the queue.
- Explicitly NOT added: a per-IP-only limiter (redundant under the global 60/min
  per-IP middleware — documented in `docs/kernel-status.md §8` so the next reader
  does not "fix" the same non-gap).

Verified: probe before (exit 1, one `pending` row) → after (exit 0, `0` stored);
HTTP probe on `php -S` (form renders the field; clean submission → 302 + 1 row;
honeypot → identical 302, +0 rows; probe rows deleted); `CommentHoneypotTest`
(4 tests, 16 assertions, the form field asserted for both theme vocabularies)
mutation-checked on the final files — neutering the check fails both discard
tests while the control stays green; full suite 293 tests / 1231 assertions /
1 skip; phpstan level 9 clean; cs-fixer clean on the changed files;
`make extract-check` and `make lekalo-check` green.

## Prevention

- **Compare sibling implementations before hardening one.** Two public forms
  doing the same job must have the same defenses; the cheapest audit is a diff
  between them. If a difference is intentional, write it down, or the next
  reader will "align" it.
- **A finding's premise needs a call-graph trace, not a file read.** Claiming
  "no limiter" from the HTTP action is wrong when the limit lives in the service
  the action calls. State where the control is and where it is not, or the fix
  lands on the wrong gap.
- **Log the non-changes too.** A deliberately redundant-looking control
  (`docs §8`: "no per-IP-only limiter, and here is why") stops the same
  non-problem from being re-fixed, and it is the only artifact that records a
  corrected finding.
- **A bot filter must not change the human path.** The honeypot test pairs the
  discard with a control that stores a clean submission, so "nothing was stored"
  can never be a broken endpoint in disguise.
- **A honeypot is rendered markup AND server-side verification** — the field
  must exist in the form (asserted in the test) or it catches nobody, however
  correct the check is.
