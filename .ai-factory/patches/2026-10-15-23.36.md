# A plaintext reset token written to a log, in every environment

**Date:** 2026-10-15 23:36
**Files:** modules/Users/Application/Services/PasswordResetService.php, modules/Users/Domain/Contracts/PasswordResetMailer.php (new), modules/Users/Infrastructure/Mail/{DevLogPasswordResetMailer,NullPasswordResetMailer,PasswordResetMailerFactory}.php (new), modules/Users/Interfaces/HTTP/AuthServices.php, modules/Users/Interfaces/HTTP/Actions/Auth/PasswordResetRequestAction.php, modules/Users/tests/{PasswordResetMailerTest.php (new),PasswordResetServiceTest.php}, .env.example, lekalo/modules/users/scenarios.yaml, docs/kernel-status.md
**Severity:** medium

## Problem

`POST /forgot-password` wrote a valid, plaintext password-reset token — beside
the address it belonged to — into `storage/logs/app.log`, in EVERY environment.
The success page also named the file for the visitor. Reproduced through the
real route with `APP_ENV=production` (php -S, port 8177): HTTP 200, an alert
naming `storage/logs/app.log`, and

```
[2026-10-15 23:30:10] [mailer:dev] Password reset for admin@example.test → token: <64 hex> (valid 1 h)
```

Reading the log was enough to take over any account that had asked for a reset.

## Root Cause

The service, not a transport, owned delivery. `requestReset()` did the work of a
mailer inline — `file_put_contents($paths->logs('app.log'), …, FILE_APPEND)` —
and the only thing standing between a live credential and the disk was a
COMMENT: "Dev mailer — log the plain token so the flow is usable without SMTP."

Why that happened, not just what:

- **A comment is not a gate.** `APP_ENV` existed in `.env.example` and was
  already read for HSTS, but "development only" was asserted in prose while the
  code had no branch at all. Anything that runs "in every environment" needs a
  line of code that says so, not a docblock.
- **The wrong owner had the capability.** Delivery is an environment fact
  (which transport exists here); the service is the business rule (always
  generate, never reveal whether the address exists). A service that both
  decides and delivers is a service that can log a credential, because it is
  holding it.
- **The flow returned the token to its caller** (`requestReset(): string`) — a
  credential handed back to an HTTP action that ignored it. Any caller could
  have logged it; one of them eventually would.
- **The visitor was told where to look.** The success message named the log file
  unconditionally, turning a backend leak into a documented one.

## Solution

Delivery moved behind a port, with the environment decision in ONE place:

- `PasswordResetMailer` (Domain/Contracts) — `sendResetLink(email, token, ttl): void`.
  `void` on purpose: the token does not travel back out of the port, so no caller
  can decide to record it. Implementations must not throw — an error for one
  address and a neutral page for another IS the enumeration oracle the flow
  avoids — so a failed delivery is logged, and the response is identical either way.
- `DevLogPasswordResetMailer` — the development transport: the old log line, with
  the log file INJECTED instead of resolved inside, so a test can assert what
  lands in it on a file it owns (this tree's `AppPaths` has no logs override).
- `NullPasswordResetMailer` — what production gets: nothing delivered, nothing
  written, same neutral answer; the drop is noted at `LOG_LEVEL=debug`.
- `PasswordResetMailerFactory` — the single gate, from a WHITELIST
  (`development`, `local`, `testing`, `test`, `dev`) rather than
  `!== 'production'`: `staging`, a typo or a new environment must not be the one
  that keeps a credential on disk. The unset default stays `development` (this
  tree's existing reading, and what makes a fresh checkout work without `.env`),
  and `.env.example` now states what each value means for reset links.
- `PasswordResetService::requestReset(): void` calls the port and nothing else;
  `AuthServices::resets()` composes them, so the environment is read once.
- The success page picks its wording from the same `writesToLog()` the transport
  choice comes from, so it can never claim a delivery that did not happen.

Verified: probe before (exit 1, token line) → after (exit 0, HTTP 200, neutral
answer, `(no new lines)`); `PasswordResetMailerTest` (5) green and
mutation-checked (forcing `create()` to always return the dev transport fails
the production case with the leaked token in the diff); full suite 289 tests /
1215 assertions / 1 skip; phpstan level 9 (gate scope) clean; `make lekalo-check`
and `make extract-check` green. Probe artifacts (the token row, `app.log`) were
removed afterwards.

## Prevention

- **A credential's whole journey must be typed.** If a value is a credential,
  no function between its creation and its destination should be able to return
  it to a caller that has no reason to hold it — `void` where a transport is the
  end of the line.
- **"Dev only" is a branch, not a comment.** Grep for eligibility claims in
  prose (`// dev`, `// for the log`, `// debug`) at any value that grants access,
  and check a line of code enforces each one.
- **Gate security-sensitive defaults with a whitelist, never a negation.** A
  `!== 'production'` gate fails OPEN for every environment name nobody listed.
- **Environment-dependent surface text is part of the behavior.** A message that
  names a file, a path or a mechanism is an assertion about configuration; it
  must be derived from the same decision the mechanism is.
- **Tests must be seen failing on the real thing.** Here: reproduce through the
  route the user hits *before* touching code (`/tmp` probe script, exit 1), then
  mutation-check the new test (force the gate open → the assertion fails with the
  leaked line) so a green suite cannot be mistaken for a working gate.
- **Editing a module means re-installing it.** Composer autoloads `Modules\` from
  `src/Modules/`, so a catalogue edit under `modules/<Name>/` is invisible to
  tests AND the running app until `bin/cms module:remove <Name> --force` +
  `module:add <Name>`. Confirm with `ReflectionClass::getFileName()`, not with a
  passing suite.
