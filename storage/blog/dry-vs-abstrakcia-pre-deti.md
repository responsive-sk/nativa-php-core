> prečo metóda aj trieda robia len jednu vec. A práve diel 3 skončil vetou, ktorou
> dnes začneme: **keď cítiš pokušenie „to by som extrahoval do spoločnej triedy“,
> príď sem.** Lebo medzi „opakujem sa“ a „vytvorím abstrakciu“ je tenká čiara ...
> a obe strany tej čiary sa dajú prestreliť.

## DRY: Don't Repeat Yourself

Predstav si, že píšeš dve kuchárske knihy a recept na palacinky je v oboch.
O rok zistíš, že palacinky potrebujú menej cukru. Opravíš prvú knihu…
a na druhú zabudneš. Teraz máš dve knihy, ktoré tvrdia dve rôzne veci
o tom istom jedle. Ktorá je pravdivá? Nevieš.

S kódom je to rovnaké. Keď je **rovnaké rozhodnutie napísané na dvoch
miestach**, máš dva zdroje pravdy. Časom sa rozídu ... niekto opraví jedno,
zabudne na druhé, a zrazu tá istá stránka ukazuje dva rôzne výsledky
podľa toho, ktorým kódom prešla.

Tomu hovoríme **DRY** ... *Don't Repeat Yourself*, neopakuj sa. Nie je to
„píš čo najmenej riadkov“. Je to **jedno rozhodnutie = jedno miesto**.
Každé pravidlo o kóde má svoje *jedno miesto pravdy*.

## Reálny prípad: `resolveCover()` na dvoch miestach

A teraz to zaujímavé ... tento repo **mal** reálnu duplicitu presne tohto
druhu, a môžeme si ju rozobrať. *(Od publikovania tohto článku bola
opravená presne podľa návodu nižšie ... `BlogArticleAction` dnes volá
`BlogArticlesService`. Kód, ktorý nasleduje, ukazuje, ako to vyzeralo
pred opravou ... a podľa neho sa naučíš duplicitu spoznať.)*

Cover obrázok článku sa vyberá podľa priority:

1. front matter `image` (autor si ho explicitne určil),
2. lokálny SVG v `storage/blog-images/{slug}.svg` (vygenerovaný),
3. Cloudinary pool (deterministický fallback podľa hashu slugu).

Toto rozhodnutie je napísané v **`BlogArticlesService`** ... službe, ktorá
robí karty na `/blog` indexe:

```php
// BlogArticlesService.php
private function resolveCover(string $slug, array $meta): string
{ // 1. Explicit image from front matter if (is_string($meta['image'] ?? null) && '' !== $meta['image']) { return $meta['image']; } // 2. Local SVG file (generated by bin/cms generate-images) $svgPath = AppPaths::instance()->storage('blog-images' . DIRECTORY_SEPARATOR . $slug . '.svg'); if (is_file($svgPath)) { return '/storage/blog-images/' . $slug . '.svg'; } // 3. Cloudinary pool fallback return self::COVER_IMAGES[abs(crc32($slug)) % count(self::COVER_IMAGES)];
}
```

…a **presne to isté** je v `BlogArticleAction` ... v action, ktorá renderuje
stránku samotného článku `/blog/{slug}`:

```php
// BlogArticleAction.php
private function resolveCover(string $slug, array $meta): string
{ // 1. Explicit image from front matter if (is_string($meta['image'] ?? null) && '' !== $meta['image']) { return $meta['image']; } // 2. Local SVG file (generated by bin/cms generate-images) $svgPath = AppPaths::instance()->storage('blog-images' . DIRECTORY_SEPARATOR . $slug . '.svg'); if (is_file($svgPath)) { return '/storage/blog-images/' . $slug . '.svg'; } // 3. Cloudinary pool fallback return self::coverPool()[abs(crc32($slug)) % 4];
}
```

Všimni si: nie sú to dve *podobné* metódy ... je to **tá istá metóda,
skopírovaná**. Rovnaké komentáre, rovnaká logika, rovnaké poradie krokov.
To nie je náhoda: jedno z dvoch miest je duplicita.

## Prečo je to nebezpečné ... a kde sa to už rozchádza

Duplicita nebolí v momente, keď ju napíšeš. Bolí pri ďalšej zmene.

Pozri
sa na posledný riadok oboch metód:

- `BlogArticlesService`: `self::COVER_IMAGES[abs(crc32($slug)) % count(self::COVER_IMAGES)]`
- `BlogArticleAction`: `self::coverPool()[abs(crc32($slug)) % 4]`

Ten rozdiel nie je len kozmetický. Pool obrázkov žije na **dvoch miestach**:
v konštante `COVER_IMAGES` v service a v metóde `coverPool()` v action.
Ako keby si recept na palacinky napísal do dvoch kníh ... a v jednej s
„3 vajcia“, v druhej s „3“.

Teraz si predstav, že niekto pridá piaty obrázok do poolu. V `BlogArticlesService`
sa o to postará sám `count(self::COVER_IMAGES)` ... zistí, že je ich 5,
a index ukáže všetkých päť. Ale v `BlogArticleAction` je natvrdo `% 4` ...
stránka článku ostane pri štyroch. Zrazu je **piaty obrázok neviditeľný**,
ale len na jednej stránke. Ako to nájdeš? Nie je žiadna chyba, žiadny
stack trace. Len dve stránky, ktoré sa nezhodujú.

A to je presne ten moment, keď duplicita prestáva byť nepríjemnosťou
a stáva sa **smoke signálom**: dve miesta s rovnakým rozhodnutím sa
časom rozídu. Nie „môžu“, ale „rozídu“ ... pretože každá zmena sa robí
na jednom mieste a druhé ostane.

## Čo s tým: jeden zdroj pravdy

Riešenie nie je napísať ešte tretiu kópiu. Riešenie je **nechať rozhodnutie
na jednom mieste a druhé miesto ho len požiadať**. V tomto prípade
`BlogArticleAction` už nemá vlastný `resolveCover()` vôbec ... existuje
služba, ktorá cover obrázok počíta, a akcia ju len zavolá:

```php
// dnes: jedno miesto rozhoduje, druhé sa pýta
$articles = new BlogArticlesService($resolver);
// …
$coverImage = $this->coverImage($slug, $meta, $articles);
```

Presne takto funguje zvyšok článkovej stránky: `BlogArticleAction`
nerozhoduje o autorovi sama, ale volá `BlogAuthorResolver`; nerobí avatar
markup, ale volá `AuthorAvatar` (diel 3). **Kompozícia namiesto kópie.**
Cover bola kedysi výnimka ... a výnimky v DRY sú presne tie miesta, kde sa
rodia bugy. Dnes je aj on kompozíciou a piaty obrázok v poole by sa
objavil na oboch stránkach naraz, lebo obe sa pýtajú tej istej metódy.

## Smoke signál, ktorý z toho zostal

A čo je na tom pekné ... duplicita nezostala len článkom. Zostala z nej
**lekcia aj regresný test**: test hliadkuje, že článková stránka a index
ukazujú pre rovnaký slug vždy rovnaký cover. Keby sa niekto k duplicite
vrátil (napríklad znova natvrdo `% 4`), test spadne ... presne tak, ako
sme sa učili v [dieli 5](/blog/smoke-test-pre-deti), že smoke testy
strážia pravidlá za teba. *(A toto je pointa celého dielu: duplicita sa dá nielen spoznať, ale aj
opraviť. Táto konkrétna bola od publikovania článku odstránená ... akcia
teraz volá `$articles->resolveCover()` a jediná kópia žije v service,
s regresným testom, ktorý stráži, že index a článok ukazujú vždy rovnaký
cover. Článok je o tom, ako duplicitu rozpoznať; oprava bola samostatná
zmena, s vlastným testom.)*

## Druhá strana mince: predčasná abstrakcia

A teraz tá druhá strana, pretože DRY sa dá zneužiť. Keď sa naučíš
„neopakuj sa“, ľahko skĺzneš do: **„tak to dám všetko za rozhranie!“**
Rozhranie je predsa abstrakcia ... jedna definícia, veľa použití, žiadna
duplicita. Znie to lákavo. Je to pasca. Rozhranie je **kontrakt pre vonkajší svet** ... zmluva, že „čokoľvek to
implementuje, bude vedieť robiť toto“. Ale keď má tvoja abstrakcia
**jedného konzumenta a jednu implementáciu**, nie je to kontrakt.
Je to dekorácia. Nič nezjednocuješ ... len pridávaš vrstvu, cez ktorú
sa musí každý čitateľ prehrýzť, aby sa dozvedel, že za ňou je
jedna jediná trieda. Prirovnanie: nekupuješ si všetko náradie do dielne vopred, „aby si ho
raz mohol použiť“. Kúpiš si skrutkovač, keď máš skrutku. Rozhranie si
vytvoríš, keď máš **druhú implementáciu** ... nie skôr.

## A toto repo to vynucuje testom (baseline 0)

To nie je len odporúčanie. V [dieli 1](/blog/co-je-cisty-kod-pre-deti)
sme si ukázali, že projekt píše pravidlá ako testy ... a aj toto je
v `tests/Architecture/CorePatternTest.php`:

```php
/** * Baseline: number of interfaces with exactly one implementation in the * same feature module and no consumer outside that module. Raising this * constant is NOT the fix ... removing a speculative interface is. */
private const SPECULATIVE_INTERFACE_BASELINE = 0;
```

Test `testNoSpeculativeSingleImplementationInterfaces()` prejde celé `src/`,
nájde každé rozhranie, spočíta jeho implementácie ... a ak má **presne jednu**
implementáciu v tom istom module a **žiadneho konzumenta** mimo neho, je to špekulatívna abstrakcia. Violation. Červený build.

A pozor na komentár ... *„raising this constant is NOT the fix“*.
Keď test spadne, pokušenie je zdvihnúť baseline z 0 na 1. Ale to je
presne ako povedať „pravidlo už neplatí“. Oprava je odstrániť špekulatívne
rozhranie ... použiť konkrétnu triedu priamo. Test je napísaný tak, aby
ťa viedol k správnej oprave, nie k vypnutiu.

## Prečo `LocalStorageProvider` nemá rozhranie

Pozri sa na skutočnú triedu z tohto repo ... `LocalStorageProvider`:

```php
// BlogArticlesService.php ... žiadne StorageProviderInterface, len konkrétna trieda
private function avatar(): AuthorAvatar
{ return $this->avatar ??= new AuthorAvatar(new LocalStorageProvider());
}
```

Volá sa priamo cez `new LocalStorageProvider()` na siedmich miestach v
projekte ... v `AuthorAvatar`, `UsersAction`, `ServeUploadedFileAction`,
`AuthorProfileAction`… A **nemá rozhranie**. Prečo? Lebo má presne jednu
implementáciu a presne jeden spôsob použitia. Keby niekto vytvoril
`StorageProviderInterface`, test `testNoSpeculativeSingleImplementationInterfaces()`
by spadol ... a to je správne. Rozhranie by nepridalo nič okrem vrstvy.

Kedy by rozhranie dávalo zmysel? Keď príde **druhý poskytovateľ** ...
napríklad `S3StorageProvider` pre produkčné nasadenie. Vtedy máš dve
implementácie, dva dôvody na výber, a kontrakt „čokoľvek, čo vie
`store()` a `delete()`, je úložisko“ sa stáva užitočným. Ale dovtedy:
konkrétna trieda, priamo, bez medzikroku.

Výnimka, ktorú test rešpektuje: rozhrania v `Modules\Core` a
`Modules\Database` sú **kontrakt zdieľaného kernelu** ... „libc headers“.
To sú rozhrania pre vonkajší svet (iné moduly), nie interná abstrakcia,
a tie baseline nepočíta.

## Rozhodovací strom: duplicita, či abstrakcia?

Keď máš pocit „toto sa opakuje“, prejdi si tri otázky ... v tomto poradí:

1. **Je to naozaj tá istá vec?** Mení sa z rovnakého dôvodu? Ak áno ... zjednoť (jeden zdroj pravdy, diel 3: jeden dôvod zmeny).
2. **Je to len podobné, ale mení sa z iného dôvodu?** Potom to nie je duplicita, je to zhoda ... a zjednotenie by bolo horšie. Dve metódy, ktoré vyzerajú rovnako, ale odpovedajú na rôzne otázky, by sa pri zjednotení začali meniť spolu. To je **predčasná abstrakcia**.
3. **Máš druhú implementáciu?** Rozhranie nie je o tom, že sa niečo opakuje ... je o tom, že existuje viac spôsobov, ako to urobiť. Jedna implementácia = žiadne rozhranie. Dve = kontrakt. A na záver jedno pravidlo, ktoré ti ušetrí najviac starostí: **abstrahuj,
keď sa duplicita objaví ... nie keď ju predvídaš.** Prvá kópia je často
v poriadku (možno sa druhá nikdy neobjaví), druhá kópia je moment, keď
začneš rozmýšľať, a tretia kópia je moment, keď zjednotíš. Nikto
nevyžaduje, aby si bol prorok ... vyžaduje sa, aby si počítal, koľko
kópií máš.

## Zhrnutie dielu 4

1. **DRY = jedno rozhodnutie, jedno miesto** ... nie čo najmenej riadkov. Dve kópie toho istého sú dva zdroje pravdy, ktoré sa rozídu.
2. **Reálny príklad** ... `resolveCover()` kedysi žil v `BlogArticlesService` aj `BlogArticleAction`, s rozchádzajúcim sa detailom (`count()` vs `% 4`), a dnes je to jeden zdroj pravdy. Presne takto vyzerá duplicita v praxi: nebolí v momente, keď ju napíšeš, bolí pri zmene.
3. **DRY sa dá zneužiť** ... „všetko za rozhranie“ je predčasná abstrakcia. Rozhranie je kontrakt pre vonkajší svet, nie dekorácia.
4. **Test to vynucuje** ... `SPECULATIVE_INTERFACE_BASELINE = 0`: rozhranie s jednou implementáciou = violation. `LocalStorageProvider` ho správne nemá.
5. **Rozhodovací strom** ... tá istá vec? Zjednoť. Podobná, ale iný dôvod zmeny? Nechaj. Druhá implementácia? Až teraz rozhranie.
6. **Odkaz na ďalší diel** ... všetky tieto pravidlá sú vynútené testami, a o tom, ako testy fungujú ako výstražné dymové signály ... a ako sa píšu tak, aby sa nedali obísť ... bude [diel 5](/blog/smoke-test-pre-deti).
